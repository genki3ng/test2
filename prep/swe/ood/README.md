# OOD / LLD — 面向对象 / 低层设计 cheatsheet

> 目标：给一个现实场景（停车场/电梯/图书馆…），25–35 分钟内设计出清晰的类结构、体现 SOLID、恰当用设计模式、能聊扩展性（有时含并发）。
> 它介于 coding 与 system design 之间：比 coding 更重抽象与可维护性，比 system design 更聚焦单机内的类与对象。配合 [../question-bank.md](../question-bank.md) 的 `oo-*` 抽题。

## 解题流程（每道题都走）

1. **澄清需求 + 圈定范围**：核心用例有哪些？先做 2–3 个主用例，确认要不要支付/并发/持久化等枝节。
2. **找名词 → 类，找动词 → 方法**：从需求里抽实体（类）、属性、行为（方法）。
3. **画类关系**：继承（is-a）、组合/聚合（has-a）、关联、多对多（常需中间类）。用枚举表示固定取值（方向/状态/类型）。
4. **套 SOLID + 模式**：让职责单一、对扩展开放；在合适处用 1–2 个设计模式并说明为什么。
5. **走一遍主用例**：用对象交互验证设计能跑通（park → findSpot → ticket → leave → fee）。
6. **聊扩展性 / 并发**：加新类型/新规则改动是否最小？有共享状态吗、怎么保护？

## SOLID（每条配一个工程例子）

| 原则 | 含义 | 例子 |
|---|---|---|
| **S** 单一职责 | 一个类只有一个变化原因 | 计费逻辑别塞进 ParkingLot，单独 FeeCalculator |
| **O** 开闭 | 对扩展开放、对修改关闭 | 加新车型/新计费策略不改已有代码 |
| **L** 里氏替换 | 子类能无缝替换父类 | Motorcycle/Car 都能当 Vehicle 用 |
| **I** 接口隔离 | 接口要小而专，别逼实现用不到的方法 | 拆 Searchable / Lendable 而非一个胖接口 |
| **D** 依赖倒置 | 依赖抽象而非具体 | 依赖 Notifier 接口，注入邮件/短信实现 |

## 常用设计模式（解决什么 → 何时用）

- **工厂 Factory**：把「创建对象」与「使用」解耦；新增类型不改调用方。→ 按类型造对象时。
- **策略 Strategy**：一族可互换算法，运行时切换。→ 计费方式、电梯调度算法、排序规则。
- **观察者 Observer**：一对多通知，发布-订阅解耦。→ 状态变化要通知多个监听者（事件/UI/通知）。
- **单例 Singleton**：全局唯一实例。→ 配置、连接池、ID 生成器；注意线程安全（双检锁/静态内部类/枚举）与可测试性争议。
- （了解）**装饰器**（动态加功能）、**适配器**（接口转换）、**状态模式**（电梯状态机可用）。

> 面试不是「用得越多越好」——用 1–2 个**贴合需求**的模式并讲清动机，比硬塞五个强。

## 经典题骨架

**停车场（`oo-01`）**
- 类：ParkingLot、Level、ParkingSpot（尺寸枚举）、Vehicle（抽象 → Car/Bus/Motorcycle）、Ticket、FeeCalculator（策略）。
- 难点：车型匹配车位规则（多态）、计费策略可换、找空位算法。

**电梯（`oo-02`）**
- 类：ElevatorSystem（调度器）、Elevator（状态机：Idle/Up/Down/DoorOpen）、Request（楼层+方向）。
- 难点：请求分配给哪部电梯（调度策略，可插拔）、同向顺路合并、内部 vs 外部请求、并发到达。

**图书馆（`oo-03`）**
- 类：Book / BookItem（多份）、Member、Catalog（检索）、Lending（借阅记录）、Fine、ReservationQueue。
- 难点：Book↔BookItem 一对多、Member↔BookItem 多对多（中间借阅记录）、借阅规则封装、状态流转。

## 并发要点（被问到时）

- **核心**：哪些状态被多线程读写？能不能不共享（不可变 / 线程封闭）？
- 同步手段：锁（互斥 / 读写锁）、原子变量（CAS）、并发容器、信号量、阻塞队列。
- 经典模型：生产者-消费者用**阻塞队列**解耦；资源池用**信号量**限并发 + 借还。
- 死锁四条件 + 预防：固定加锁顺序、加超时、避免嵌套锁。
- 讲清你的**锁粒度权衡**（粗锁简单但并发低 / 细锁并发高但易错）。

## 评估你的设计（自检）

- [ ] 每个类职责单一、命名清楚。
- [ ] 关系（继承/组合）用得对，没有滥用继承。
- [ ] 加一个新类型 / 新规则，需要改几处？越少越好。
- [ ] 用的模式是否真的解决了一个具体问题（而非炫技）。
- [ ] 主用例能用对象交互讲通。
