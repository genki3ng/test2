# 管道 / 系统设计（DE 设计轮）

> **高级岗的分水岭**。考的不是"能不能跑通"，而是 **trade-off、规模、可靠性、成本、可维护性**，以及"何时不该这么做"。答题套框架：澄清需求 → 画端到端数据流 → 逐组件下钻 → 主动报坑与取舍。
> 配套抽题：[../question-bank.md](../question-bank.md) 的「数据系统设计」类（ds-01 ~ ds-05）。

## 答题框架（任何设计题先走这五步）

1. **澄清需求**：数据规模（GB/TB/PB）、延迟要求（天/小时/分钟/秒）、查询模式、谁是下游、SLA、预算。**不澄清就动手 = 扣分**。
2. **画端到端数据流**：来源 → 摄取 → 存储/计算 → 服务/下游。先整体后局部。
3. **逐组件下钻**：每个环节讲选型 + 为什么 + 备选。
4. **可靠性**：幂等、回填、失败重试、数据质量、监控。
5. **取舍收尾**：你的推荐 + 理由 + 已知局限 + 何时换方案。

## Cheatsheet 1：批 vs 流

| | 批处理 | 流处理 |
|---|---|---|
| 延迟 | 高（小时/天） | 低（秒/分） |
| 吞吐/成本 | 高吞吐、便宜 | 持续运行、贵 |
| 复杂度 | 简单、易回填重算 | 状态/乱序/容错/回填都难 |
| 适合 | 报表、训练集、不敏感聚合 | 监控、风控、实时大盘 |

**流的核心难点**：
- **事件时间 vs 处理时间**：按事件发生时间计算才正确；
- **watermark**：判定"某时间窗口数据到齐了"、处理迟到数据的机制；
- **窗口**：滚动（tumbling）/ 滑动（sliding）/ 会话（session）；
- **状态后端 + checkpoint**：容错与恰好一次的基础。

**架构**：
- **Lambda**：批层保真 + 流层提速，结果合并；痛点是维护两套逻辑。
- **Kappa**：只用流 + 可重放日志（Kafka 长留存），回填靠重放，一套代码。

> 选型先问业务对延迟与回填的**真实**需求，别为"实时"而实时。

## Cheatsheet 2：幂等（idempotency）与回填（backfill）—— DE 灵魂考点

**幂等** = 同一输入重复执行结果一致，是分布式管道容错/重试安全的基石。

实现手段：
- **整分区覆盖**：`INSERT OVERWRITE PARTITION (dt=...)` 先删后写，重跑该分区结果幂等。
- **upsert / merge**：按主键 `MERGE INTO`，重复写入不翻倍。
- 写前生成**确定性去重键**。

反模式（必避）：盲目 `INSERT INTO ... APPEND`（重跑翻倍）；依赖 `now()`/当前时间使重算漂移。

**回填**：把执行日期 `dt` 作为**参数**，按分区逐日重跑历史。得益于幂等，回填 = 对历史分区重新执行同一套逻辑。注意：
- 用**事件时间对齐当时的维度/SCD 版本**，不能拿今天的维度算历史事实；
- 控制并发与资源，别一次性回填把集群打爆；
- 回填顺序按依赖（先上游后下游）。

## Cheatsheet 3：分区（partitioning）

- **目的**：分区裁剪（只扫相关分区）、并行、便于按分区幂等覆盖与回填。
- **分区键选择**：最常按 `dt`（日期）；高基数维度（如 user_id）直接当分区键会产生海量小分区——慎用，或用分桶（bucketing）。
- **小文件问题**：分区过细 + 流式频繁写 → 大量小文件拖垮元数据与读性能 → 定期 compaction / 写前 `coalesce`。
- **分区 ≠ 索引**：分区是物理目录切分；想点查还需排序/分桶/ZORDER 等。

## Cheatsheet 4：数据质量与 SLA / 可观测性

**质量维度**：完整性（行数/分区到齐）、唯一性（主键不重）、有效性（取值域/格式）、一致性（与上游对账）、时效性（按时产出）、准确性（关键聚合校验）。

**落地**：
- 管道里嵌**断言/测试**：行数突变、空值率、主键唯一、外键命中率、关键指标环比阈值。
- 失败即**阻断下游**（circuit breaker），坏数据不外溢。
- **SLA/SLO**：约定"每天 X 点前产出、可用率 99.x%"；监控**新鲜度（freshness）** + 延迟告警。
- **血缘（lineage）**：上下游可追溯，出问题快速定位影响面与根因。
- **数据契约（data contract）**：与上游约定 schema/语义/SLA，变更走流程——防"上游悄悄改字段打挂下游"。
- 可观测性三件套：**新鲜度、量级、schema/分布漂移** 的持续监控 + 告警 + 值班。

## Cheatsheet 5：调度 / DAG（Airflow 思想）

- **DAG**：显式声明任务依赖（A 完成才跑 B），调度器按拓扑序触发。任务应**幂等、可重试、原子**。
- **触发**：定时（schedule_interval）+ **数据就绪传感**（sensor 等上游分区/文件到齐），避免"算空气"。
- **失败处理**：重试 + 退避、超时、SLA miss 告警；只重跑失败节点及其下游（不重跑整图）。
- **回填**：参数化逻辑日期（execution_date），按区间补跑；注意 catchup 行为别炸集群。
- **资源隔离**：任务池/并发上限、按队列分资源。
- **现代趋势**：从"时间触发任务"转向"**数据资产化 / 数据触发**"（asset-aware，如 Dagster/dbt 思路）——关注产出资产是否新鲜，而非任务跑没跑。

## Cheatsheet 6：CDC / 文件格式 / Lakehouse

**CDC（Change Data Capture）**：把业务库（MySQL/Postgres）变更近实时同步到数仓。
- 读 **binlog**（Debezium 思路）捕获 insert/update/delete → Kafka → 落数仓；优于定时 `SELECT *`：不漏更新与删除、对源库压力小、近实时、保留变更顺序。
- 落地：snapshot 全量初始化一次 + 增量持续追；按主键 **upsert**，delete 用软删标记（分析常要"删了也能看历史"）；用 binlog 偏移/事务时间排序 + 下游幂等 = 实际 exactly-once 效果。

**文件格式**：
- **行存（CSV/Avro）** 适合写入/整行读取；**列存（Parquet/ORC）** 适合分析——列裁剪 + 谓词下推 + 高压缩，OLAP 默认。
- Parquet 三大利器：只读需要的列、跳过不相关 row group（min/max 统计）、按列编码压缩。

**Lakehouse（表格式：Iceberg / Delta / Hudi）**：在对象存储的文件上加一层表格式，带来——
- **ACID 事务**、**schema 演进**（加列不重写）、**时间旅行**（按版本/时间查历史）、**upsert/merge**、隐藏分区与 compaction。
- 价值：兼得数据湖的低成本/开放格式 与 数仓的可靠性/可管理性。
