## SQL & 数据建模

### [sm-01] 用窗口函数算每个用户每月的累计消费与环比
给一张 `orders(user_id, order_ts, amount)`，求每个用户每个自然月的消费总额、截至当月的累计额（running total）、以及相对上月的环比变化。
**要点**
- 先 `date_trunc('month', order_ts)` 聚出月度 `SUM(amount)`，这是后续窗口的输入。
- 累计：`SUM(monthly_amt) OVER (PARTITION BY user_id ORDER BY month ROWS UNBOUNDED PRECEDING)`；显式写 frame 避免默认 `RANGE` 在并列行上的坑。
- 环比：`LAG(monthly_amt) OVER (PARTITION BY user_id ORDER BY month)`，第一行 NULL 用 `COALESCE` 或留空说明。
- 月份有空洞（某月无单）时，标准答案是先 `cross join` 一张月历表补齐再算，否则环比会"跳月"。
- 讲清 `PARTITION BY` vs `GROUP BY`：窗口不折叠行，聚合折叠行。

### [sm-02] 多种去重写法及各自代价
表里有重复行（完全重复 + 业务主键重复但其他列不同两种情况），讲清你会怎么去重。
**要点**
- 完全重复：`SELECT DISTINCT` 或 `GROUP BY 全列`；大表上 `DISTINCT` 触发全量 shuffle，代价高。
- 按业务键保留一条：`ROW_NUMBER() OVER (PARTITION BY 主键 ORDER BY 更新时间 DESC) = 1`，明确"保留最新/最早"的排序键，避免不确定结果。
- `QUALIFY`（Snowflake/BigQuery）可直接过滤窗口结果，比子查询包一层干净。
- 去重前先问：重复是数据质量问题（上游重发）还是天然多行？根因在管道里用幂等/dedup 解决，不要每次查询都补救。
- 计数去重 `COUNT(DISTINCT x)` 在超大基数上昂贵 → 可接受误差时用 `APPROX_COUNT_DISTINCT`（HLL）。

### [sm-03] 写一个留存 / 漏斗查询
求"注册后第 1/7/30 日仍活跃"的留存率；或求"浏览→加购→下单→支付"的漏斗各步转化。
**要点**
- 留存：以注册日为锚（cohort），`LEFT JOIN` 活跃事件，按 `DATEDIFF(active_day, signup_day)` 落到第 N 日，分母是 cohort 规模。
- 注意分母口径：是 day-N 留存（恰好第 N 天活跃）还是 N-day 留存（N 天内活跃过），面试要主动澄清。
- 漏斗：每步用 `COUNT(DISTINCT user_id)` 且要求"有序"——后一步必须发生在前一步之后，用 `MIN(step_ts)` 比较或 self-join 带时间约束。
- 用户可能重复进入漏斗：明确按"首次完成路径"还是"任意路径"统计。
- 大规模漏斗常预聚合成"用户×步骤首次时间"宽表，再算转化，避免反复扫事件流。

### [sm-04] 维度建模：星型 vs 雪花、事实表 vs 维度表
设计一个电商分析的数仓模型，讲清事实表、维度表怎么分，星型和雪花的取舍。
**要点**
- 事实表：记录"发生的事"（订单、点击），窄而长，存度量值（measure）+ 外键，按时间分区；区分事务事实 / 周期快照 / 累积快照三类。
- 维度表：描述"上下文"（用户、商品、门店、日期），宽而短，存可读属性供切片/下钻。
- 星型：维度直接挂事实表，反范式、JOIN 少、查询快——分析场景默认首选。
- 雪花：维度再拆子维度（规范化），省存储、利于维护一致性，但 JOIN 变多、查询更慢。
- 一致性维度（conformed dimension）：跨多个事实表共用同一维度（如统一的"日期维""用户维"），是企业级一致性的关键。
- 度量的可加性：完全可加 / 半可加（如库存余额不能跨时间求和）/ 不可加（如比率），决定能否随便 SUM。

### [sm-05] 缓慢变化维（SCD）Type 1/2/3 怎么选
用户把城市从北京改到上海，历史订单的"用户城市"该显示哪个？讲 SCD 三型。
**要点**
- Type 1：直接覆盖旧值，不留历史。简单，但丢掉了"当时是什么"，分析历史会被改写。
- Type 2：插入新版本行 + `effective_from / effective_to / is_current` 标记（或版本号），保留完整历史，是最常用的"既要现状又要历史"方案；事实表 JOIN 时按事件时间落在哪个有效区间取对应版本。
- Type 3：加一列"前值"（如 `current_city` + `previous_city`），只能留有限历史，适合"只关心上一版"的场景。
- 实务里常 Type 1 与 Type 2 混用：易变且无分析价值的属性用 1，需追溯的关键属性用 2。
- 代理键（surrogate key）：Type 2 下同一自然键有多行，用自增代理键做事实表外键，才能精确指向某个时间版本。

### [sm-06] 范式 vs 反范式、增量 vs 全量
什么时候规范化、什么时候反范式？批处理该全量重算还是增量更新？
**要点**
- 范式（3NF）：消冗余、写一致，适合 OLTP / 数据采集层（ODS）；分析时 JOIN 多、慢。
- 反范式：宽表预 JOIN、冗余存储，适合 OLAP / 服务层，读快但写放大、需保证冗余字段同步。
- 经验法则：底层规范化保真，上层（mart/宽表）反范式提速；用建模分层（ODS→DWD→DWS→ADS 思路）兼得。
- 全量：每次重算整张表，简单、自愈（修了 bug 重跑即对），但贵、慢，适合小表或逻辑频繁变。
- 增量：只处理新增/变更分区（按 `dt` 或 watermark），快、省，但需处理迟到数据、去重、回填，复杂度高。
- 折中：增量为主 + 周期性全量校正（lambda 思路）；增量务必设计成幂等，重跑同一分区结果一致。

## Coding

### [cd-01] 不把全文件读进内存，统计超大日志里 Top-K
一个几十 GB 的日志文件，单机内存放不下，求出现次数最多的 K 个 URL。
**要点**
- 流式逐行读（generator / `for line in file`），绝不 `read()` 全量进内存。
- 若不同 key 的基数也大到放不下 dict：先按 `hash(url) % N` 分桶到 N 个临时文件，再逐桶在内存里统计（外部分治 / external hashing）。
- 每桶内统计完用大小为 K 的最小堆（`heapq.nlargest` 或维护 heap）求 Top-K，避免对全量排序。
- 复杂度：分桶 O(n)，堆求 Top-K 是 O(n log K) 远优于 O(n log n) 全排序。
- 工程视角：这正是 MapReduce/Spark 的 word-count，单机题答完可引申到分布式怎么做。

### [cd-02] 用 Python 合并 / 去重两个大数据源
两份用户记录（可能有重叠、字段冲突），合并成一份并按规则去重，讲实现与边界。
**要点**
- 用 dict 以主键聚合，冲突时按规则取（最新时间戳 / 非空优先 / 来源优先级），把"冲突解决规则"显式说出来。
- pandas 路线：`merge`（注意 `how` 与 `validate=` 校验基数）、`drop_duplicates(subset=, keep=)`、`combine_first` 填空。
- 数据量超内存：分块 `read_csv(chunksize=)` 流式处理，或直接上 Spark/DuckDB，别死磕单机 pandas。
- 边界：主键为空、重复主键、类型不一致（"1" vs 1）、大小写/空格、时区——主动列出。
- 讲清时间/空间复杂度：哈希聚合 O(n) 时间、O(唯一键) 空间。

### [cd-03] Spark 数据倾斜（skew）怎么定位与解决
一个按 user_id 的聚合作业，某些热点 key 导致个别 task 跑很久、其余早完，怎么办？
**要点**
- 定位：Spark UI 看 stage 里 task 的耗时/输入分布——少数 task 数据量远超中位数即倾斜；或抽样统计 key 频次。
- 加盐（salting）：给热点 key 拼随机后缀 `key_0..key_n` 打散，先局部聚合再去盐二次聚合（两阶段聚合）。
- 倾斜 JOIN：大表小表用 broadcast join 避免 shuffle；大表大表且单边热点可对热点 key 单独处理（skew join）或 AQE 自动切分。
- 开启 AQE（Adaptive Query Execution）：`spark.sql.adaptive.enabled` + `skewJoin.enabled`，运行时自动拆分倾斜分区。
- `reduceByKey` / `aggregateByKey` 优于 `groupByKey`（前者 map 端预聚合，shuffle 量小）。

### [cd-04] 讲清 Spark shuffle、宽窄依赖、分区与并行度
什么操作触发 shuffle？宽依赖窄依赖是什么？并行度怎么定？
**要点**
- 窄依赖：父分区→子分区一对一/多对一（`map`/`filter`/`union`），无需跨节点传数据，可在同一 stage 流水线执行。
- 宽依赖：子分区依赖多个父分区（`groupByKey`/`join`/`repartition`/`distinct`），触发 **shuffle**——落盘 + 网络传输，是 stage 边界与性能瓶颈。
- shuffle 代价：磁盘 IO + 网络 + 序列化；优化方向是减少 shuffle 数据量（map 端预聚合、列裁剪、过滤前置、broadcast）。
- 分区数：`spark.sql.shuffle.partitions`（默认 200，按数据量调）；分区太少→单 task 过大/OOM，太多→调度开销大、小文件多。
- 并行度经验值：总核数的 2–4 倍；`repartition`（带 shuffle、均匀）vs `coalesce`（无 shuffle、只能减、可能不均）要分清。
- `cache/persist` 复用多次的中间结果；注意存储级别与内存压力。

## 数据系统设计

### [ds-01] 设计一条把业务库数据同步到数仓的管道（CDC）
上游是 MySQL 业务库，要近实时同步到数仓供分析，怎么设计？
**要点**
- 全量初始化（snapshot）一次 + 增量 CDC 持续追：读 binlog（Debezium 思路）捕获 insert/update/delete，进 Kafka，再落数仓。
- 为什么用 CDC 而非定时 `SELECT *`：不漏更新与删除、对源库压力小、近实时、能拿到变更顺序。
- 数仓侧落地：先进入只追加的变更日志层，再 merge/upsert 成当前态表；或保留全历史做 SCD2。
- 处理 update/delete：按主键 upsert；delete 用软删标记位（很多分析要"删了也要能看历史"）。
- 乱序与一次性语义：用 binlog 偏移/事务时间排序，下游幂等 upsert 保证重放安全（at-least-once + 幂等 = 实际 exactly-once 效果）。
- schema 演进：上游加列怎么自动传导；用支持 schema evolution 的格式（如 lakehouse 表格式）。

### [ds-02] 批处理 vs 流处理怎么选，各自的 trade-off
同一个指标，什么时候用批、什么时候用流？
**要点**
- 批：高吞吐、逻辑简单、易回填重算、成本低、延迟高（小时/天级）；适合报表、训练集、对延迟不敏感的聚合。
- 流：低延迟（秒/分级）、持续计算，但状态管理、乱序、容错、回填都更复杂、成本高；适合监控、风控、实时大盘。
- 流里的核心难点：事件时间 vs 处理时间、watermark 处理迟到数据、窗口（滚动/滑动/会话）、状态后端与 checkpoint。
- Lambda 架构：批层保真 + 流层提速，结果合并；维护两套逻辑是其痛点。
- Kappa 架构：只用流 + 可重放日志（Kafka 长留存），回填靠重放，简化为一套代码。
- 选型先问业务对延迟的真实要求与回填诉求，别为了"实时"而实时。

### [ds-03] 幂等（idempotency）与回填（backfill）怎么设计
调度重跑、补历史数据时，怎么保证结果不重复、不出错？
**要点**
- 幂等 = 同一输入重复执行结果一致。是分布式管道容错与重试安全的基石（任务失败重跑不会双写）。
- 实现手段：① 按分区"先删后写"（`INSERT OVERWRITE PARTITION dt=...`）整分区替换；② upsert/merge 按主键；③ 写前生成确定性的去重键。
- 严禁的反模式：盲目 `INSERT INTO ... APPEND` 重跑会翻倍；依赖"当前时间"`now()` 使重算结果漂移。
- 回填：用同一套参数化逻辑（把 `dt` 作为参数）按分区逐日重跑历史；得益于幂等，回填 = 对历史分区重新执行。
- 回填注意：维度/SCD 的"当时状态"要用事件时间对齐，不能用今天的维度去算历史事实；控制并发与资源避免冲垮集群。
- 设计期就把"可重跑、可回填"当硬需求，而非事后补救。

### [ds-04] 数据质量与 SLA：怎么保证下游"敢用"
你的表每天产出，下游报表依赖它，怎么保障质量和及时性？
**要点**
- 质量维度：完整性（行数/分区是否到齐）、唯一性（主键不重）、有效性（取值域/格式）、一致性（与上游对账）、时效性（按时产出）、准确性（关键聚合校验）。
- 落地检查：管道里嵌断言/测试（行数突变、空值率、主键唯一、外键命中率、与昨日环比阈值），失败即阻断下游（circuit breaker）。
- SLA / SLO：约定"每天 X 点前产出、可用率 99.x%"；用数据"新鲜度"（freshness）监控 + 延迟告警。
- 血缘（lineage）：知道这张表上游是谁、下游是谁，出问题能快速定位影响面与根因。
- 数据契约（data contract）：与上游约定 schema/语义/SLA，上游变更需走流程，防止"上游悄悄改字段"打挂下游。
- 可观测性三件套：新鲜度、量级、schema/分布漂移的持续监控 + 告警 + 值班。

### [ds-05] 调度 / DAG（Airflow 思想）怎么编排依赖
几十个相互依赖的任务，怎么编排、保证顺序、处理失败？
**要点**
- 用 DAG 显式声明任务依赖（A 完成才跑 B），调度器按拓扑序触发；任务应是幂等、可重试、原子的算子。
- 触发方式：定时（cron/schedule_interval）+ 数据就绪传感（sensor 等上游分区/文件到齐再启动），避免"算了个空气"。
- 失败处理：重试次数 + 退避、超时、SLA miss 告警、失败只重跑失败节点及其下游（不重跑整图）。
- 回填：参数化执行日期（execution_date / 逻辑日期），按日期区间补跑历史；注意 catchup 行为别炸集群。
- 隔离与资源：任务池/并发上限、按队列分资源；幂等保证手动重触发安全。
- 现代趋势：从"时间触发"转向"数据触发/资产化"（asset-aware），关注产出的数据资产是否新鲜，而非任务跑没跑。

### [bh-01] 用 STAR 讲一次你主导的数据管道 / 平台改进
讲一个你 owned 的、有量化影响的数据工程项目。
**要点**
- Situation/Task：一句话讲清痛点与你的职责（如"核心管道每天延迟、下游频繁拿到隔夜数据"）。
- Action：突出你的技术判断与权衡（为什么这么设计、否决了什么方案），而非流水账。
- Result：量化——延迟从 X 降到 Y、成本降 Z%、SLA 达成率、影响的下游/用户数。
- DE 信号：可靠性、可维护性、成本、规模、对下游的同理心。
- 结尾点出可迁移的经验或后续影响（被复用、立了规范）。

### [bh-02] 讲一次数据事故 / 数据质量问题的复盘
线上数据出错或管道挂了，你怎么处理、怎么防止再犯？
**要点**
- 先讲影响与止血：怎么发现（监控告警 vs 下游投诉——前者更好）、影响范围评估、先恢复服务/回填正确数据。
- 根因分析：用 5 Why 或时间线，定位是上游 schema 变更 / 迟到数据 / 代码 bug / 资源问题。
- 系统性预防：补监控/断言、加数据契约、改成幂等可回填、写 runbook——强调"修流程不只修这一次"。
- 体现 ownership 与 blameless 文化：对事不对人，沉淀为团队改进。
- 量化：MTTR、此后同类事故下降、新增的护栏拦下过多少次。

### [bh-03] 讲一次跨团队协作 / 影响他人
和上游团队、下游分析/产品就数据需求或质量产生分歧，怎么推进？
**要点**
- 背景：典型场景是上游频繁改 schema 打挂你，或下游对口径有分歧。
- Action：用数据/影响说话（量化 breakage 次数与成本），推动达成数据契约 / 评审流程 / 统一口径；倾听对方约束、给对方也省事的方案。
- 沟通：把技术问题翻译成业务语言让非技术方理解优先级。
- Result：流程落地、breakage 下降、协作关系改善，最好成为团队标准。
- 体现资深信号：不是吵赢，而是建立机制让问题不再反复发生。
